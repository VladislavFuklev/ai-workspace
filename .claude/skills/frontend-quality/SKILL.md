# Frontend Quality

Stack as installed: Next.js 16.3.5 (App Router, Turbopack), React 19.2.8,
TypeScript 5, Tailwind CSS 4. TanStack Query, React Hook Form and Zod arrive in
phase 1.

## Read the bundled docs first

`apps/web/AGENTS.md` carries a warning worth taking literally: **this is not the
Next.js in your training data.** Version 16 changed APIs, conventions and file
structure. Before writing anything that touches a Next.js API — routing, caching,
`fetch` semantics, params, metadata, route handlers, middleware — read the relevant
page under `node_modules/next/dist/docs/01-app/` resolved from `apps/web/`.

Guessing here produces code that looks right, typechecks, and is wrong. Check the
doc; it costs one file read.

Related: `apps/web/AGENTS.md` and `apps/web/CLAUDE.md` are regenerated by
`next dev`. Commit them with your work; deleting them just re-creates the diff.

## Layers

```
app → features → components → lib
```

- `app/` — routing, layouts, loading/error boundaries, metadata, route handlers.
  Thin. A page composes a feature; it does not implement one.
- `features/` — a vertical slice (documents, chat, auth, organizations, usage):
  its components, hooks, API calls and types. **A feature never imports another
  feature's internals.** When two need the same thing, it moves down to
  `components/` or `lib/`.
- `components/` — presentational and primitive components with no product
  knowledge. A component in here must be usable by any feature.
- `lib/` — API client, query client, validation schemas, formatting, utilities.
  No React state, no feature knowledge.

Directories are created when their first real file exists, not as placeholders.

## Server and client boundary

This is the decision that most affects both correctness and bundle size.

- Server Components are the default. Add `"use client"` only for the reason it
  exists: state, effects, browser APIs, or event handlers.
- Push `"use client"` **down** the tree. A client boundary on a layout drags
  everything below it into the bundle. A leaf that needs `useState` should be the
  client component, not its parent.
- Never let a secret, API key, or internal URL reach a client component. Anything
  in a client component's props or module scope is shipped to the browser.
- Server Components can be async and fetch directly. Do not add a client-side
  fetch for data the server could have rendered.
- Serialization: only serializable values cross the server→client boundary. No
  functions, class instances, or `Date` assumptions without checking.

## Data fetching and cache

- One API client in `lib/`, one place that sets base URL, auth headers, error
  normalization and timeouts. Never call `fetch` to the API from a component.
- TanStack Query (phase 1.8) owns client-side server state. Query keys are
  structured and centralized, not string literals typed at each call site — a typo
  in a key is a cache miss that looks like a bug.
- Invalidate on mutation. Decide `staleTime` deliberately per resource rather than
  accepting a default everywhere.
- Distinguish the four states in the UI every time: loading, empty, error, success.
  "It flashes empty then fills in" is a bug, not a state.
- Never render an AI response or document content as HTML without sanitizing.
  Treat model output and uploaded documents as hostile input.

## TypeScript

- `strict` is on. Do not weaken it, and do not add `any` — if a type is unknown,
  it is `unknown` and you narrow it.
- No `as` to silence an error. A cast that is not a genuine narrowing is a lie the
  compiler will stop protecting you from.
- No `@ts-expect-error` without a comment saying why and what removes it.
- Type at the boundary: parse API responses with Zod at the edge (phase 1.7/1.9) so
  the rest of the app has real types rather than asserted ones.
- `pnpm typecheck` runs `next typegen` first — Next 16 generates the global route
  types (`LayoutProps`, `PageProps`) that `tsc` needs. A bare `tsc` fails on a
  clean tree.

## Forms

React Hook Form plus a Zod resolver, with the same Zod schema shared between
client validation and the API contract where possible. Requirements:

- Validation errors tied to inputs via `aria-describedby`, announced, not only red.
- Submit disabled while pending, with a visible pending state.
- Server-side errors mapped back onto the offending field, not dumped in a banner.
- The form must work with the keyboard alone, and survive a browser autofill.

## Accessibility — non-negotiable, not a phase-12 chore

- Semantic elements first. A `div` with `onClick` is not a button: no focus, no
  Enter/Space, no role.
- Every interactive element is reachable and operable by keyboard, with a visible
  focus ring. Never remove the outline without replacing it.
- Contrast at least 4.5:1 for body text, 3:1 for large text and UI boundaries.
- Icon-only controls need an accessible name.
- Modals and menus: focus trapped, `Escape` closes, focus returns to the trigger.
- Content that updates asynchronously (streaming answers, toasts) needs a live
  region, or a screen reader user learns nothing happened.
- Respect `prefers-reduced-motion`.

## Performance

- Watch what crosses into the client bundle; a client boundary high in the tree is
  the usual cause of a large bundle.
- `next/image` for images, with dimensions, to avoid layout shift.
- `next/font` rather than a blocking stylesheet from a font CDN.
- Virtualize long lists (document lists, chat history) before they get long.
- Streaming AI responses must not re-render the whole conversation per token.
- Measure before optimizing; `rtk next build` prints route sizes.

## Design bar

The product must not look like a generated dashboard. Concretely: one restrained
palette with a real neutral ramp, one spacing scale used consistently, a typographic
hierarchy with no more than three sizes per screen, and density that suits real
data. No gradient headers, no glassmorphism, no giant rounded cards in a grid of
three, no fabricated metrics. Design tokens land in 1.3 — use them, do not hardcode
colors afterwards.

## Review checklist

- [ ] Checked the bundled Next 16 doc for any framework API used
- [ ] `"use client"` only where required, pushed as far down as possible
- [ ] No secret reachable from a client component
- [ ] No cross-feature internal import
- [ ] All API calls go through the `lib/` client
- [ ] Loading, empty, error and success states all implemented
- [ ] No `any`, no silencing cast, no undocumented `@ts-expect-error`
- [ ] Keyboard path works; focus visible; names on icon buttons
- [ ] Verified at ~375px, ~768px and desktop; no horizontal overflow
- [ ] Long text, long names and empty collections do not break the layout
