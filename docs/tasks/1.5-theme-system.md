# Task 1.5 — Theme system

## Objective

A three-way theme control (light, dark, follow the system) that persists, applies
before first paint, and works with no JavaScript at all.

## Context

0.8 defined the tokens and the `data-theme` mechanism but shipped no control, and
left a real bug: the `prefers-color-scheme` block set only `color-scheme`, so a
visitor whose system is dark got the light palette.

## Implementation steps

1. Fix the system-preference path so it applies the dark tokens.
2. Inline script in `<head>` applying a stored choice before paint.
3. `ThemeToggle` as a radiogroup — "system" is a third state a toggle cannot express.
4. Persist in `localStorage`; "system" stores nothing and removes the attribute.
5. Guard every storage access: it throws in some privacy modes.

## Acceptance criteria

- No flash: the theme script runs before `<body>`.
- Dark applies from a stored choice **and** from the system preference with no JS.
- The control is a labelled radiogroup with three named options.
- A private-mode storage failure does not break the page.
- `scripts/check.sh` passes.

## Tests

Verification is the served markup (script position, ARIA) and the built CSS
containing both dark branches.

### Deviations
- **Fixed a 0.8 bug rather than only adding the control.** The
  `prefers-color-scheme` block set `color-scheme` but not the tokens, so system
  dark rendered the light palette. Now a `:root:not([data-theme])` block carries
  the full dark set.
- **The dark tokens are deliberately duplicated** — once for the explicit
  attribute, once for the media query — because CSS cannot share one declaration
  block across both. The duplication is an asserted invariant, not a hope: drift
  would otherwise only show for people with dark mode and slow JS.
- **`light-dark()` was tested and rejected.** It removes the duplication, but
  Lightning CSS transpiles it into `var(--lightningcss-light,…)var(--lightningcss-dark,…)`,
  which is an opaque artifact to depend on and to check.
- **`useSyncExternalStore`, not `useState` in an effect.** The first version set
  state from an effect and wrote the DOM attribute from the click handler; the
  React Compiler lint rules rejected both — cascading renders, and mutating
  something outside the component. The preference genuinely lives outside React,
  so it is now an external store, with the DOM write in an effect. That also
  hydrates from the server's "system" without a mismatch, and keeps other tabs in
  step via the `storage` event.

### Known limitations
- Switching does not animate. Deliberate — a cross-fade of every surface is the
  kind of motion that reads as lag.
- Only reasoned, not observed in a browser: no automation until 12.8.
