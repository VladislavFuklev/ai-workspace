# Task 3.9 — Frontend auth flows

## Objective

Sign in, sign up and request a reset, in both locales, against the endpoints
phase 3 built.

## Context

1.9 supplied the form primitives, 1.11 the catalogues, 1.7 the API client with
`credentials: "include"`. The API's contract is codes, not messages (ADR-015), so
the client owns every sentence a user reads.

## Implementation steps

1. `features/auth/` — schemas, API calls, a current-user hook.
2. `authErrorKey` — an `ApiError` becomes a message key.
3. Three forms and three pages under an `(auth)` group.
4. Catalogue entries in both locales, including validation messages.

**Excluded:** the route guard and sign-out (3.10), the reset-confirm screen,
which needs a token that nothing can deliver yet (3.7).

## Acceptance criteria

- All three pages render in both locales with translated headings.
- Validation messages are translated, not English under a Ukrainian label.
- Sign-in failure shows one generic message.
- Sign-up shows the same confirmation whether or not the address was taken.
- A server-side 422 lands on the offending field.
- `scripts/check.sh` passes.

## Tests

12.2 owns component tests. Verified against a running API and web server.

### Deviations
- **Validation messages come from the catalogue**, so the Zod schema is built
  inside the component where `t` is available. A module-level schema would have
  meant English messages under Ukrainian labels.
- **Sign-up shows a confirmation panel rather than redirecting.** ADR-018 makes
  the response identical for a taken address, and a redirect into the app would
  have leaked the difference the API refuses to state.
- **`useCurrentUser` treats 401 as `null`, not an error.** It is the answer
  "nobody", and letting it through would put a red banner on every signed-out
  page.
- **No reset-confirm screen.** It needs a token from an email that nothing sends
  (3.7); building the screen would suggest a flow that cannot complete.

- **Verifying by hand against the shared database broke three tests**, and the
  cause was in the tests rather than the data: they asserted on *every* session
  row instead of the user's. A row from any other sign-in — mine, from a curl
  check — made them fail. They are now scoped by `user_id`. Worth remembering:
  a global assertion against a shared database is a test that depends on
  everything that ever ran.

### Known limitations
- No component tests until 12.2; verified by rendering and by the round trip.
- Keyboard and screen-reader behaviour is reasoned from the `Field` primitives
  (1.9), not observed.
- Nothing signs the user out yet, and no route is protected — 3.10.
