# Task 2.5 — Alembic migrations

## Objective

Schema changes through migrations only, with a first revision that makes the
`vector` extension available on every path — not just the two that already
have it.

## Context

The extension is created by the compose init script (0.3) and was created in CI by
a helper script (2.3). Neither covers a managed database or a fresh deployment.
2.4 fixed the naming convention autogenerate depends on.

## Implementation steps

1. `alembic init -t async`, then rewrite `env.py` to read the URL from the
   application's settings rather than `alembic.ini`.
2. `compare_type` and `compare_server_default` on, or autogenerate silently misses
   a column changing type or nullability.
3. First revision: create the extension; downgrade documented as a no-op.
4. Align `script.py.mako` with the project's style.
5. CI runs `alembic upgrade head` instead of the helper script; delete the script.
6. Tests: single head, every revision declares a downgrade, and models do not drift
   from the schema.

## Acceptance criteria

- `alembic upgrade head` creates the extension on an empty database.
- `downgrade base` succeeds and is a documented no-op.
- The history has exactly one head.
- Autogenerate finds nothing after `upgrade head`.
- The drift check is proven able to fail.
- `scripts/check.sh` passes.

## Tests

Unit for history shape; integration for drift.

### Deviations
- **The URL comes from the application's settings, not `alembic.ini`.** The line
  in the ini is commented out. A migration run against a different database than
  the app is the classic way a schema and a deployment drift apart.
- **CI runs `alembic upgrade head`** rather than the helper script from 2.3, which
  is deleted. Running the migrations in CI also tests them: a broken revision
  fails there instead of during a deployment.
- **The `downgrade` is empty and says why.** Dropping the extension would take
  every vector column with it. An irreversible step is better stated than
  pretended.
- **Test tables moved to their own metadata (`ScratchBase`).** A scratch table on
  `Base.metadata` made the drift check report a difference that did not exist —
  and the first version of that check papered over it with a filter instead. Also
  not named `Test*`, which pytest tries to collect.
- **The drift check is close to vacuous** with no domain models, so a second test
  introduces a table missing from every migration and asserts it is caught. A
  check nobody has seen fail is not a check.

### Known limitations
- No test runs migrations against a database created from scratch in isolation;
  the drift check runs against the shared development database. Worth revisiting
  at 12.5 with a per-run database.
- Creating an extension needs elevated rights on a managed Postgres; documented
  in the revision.
