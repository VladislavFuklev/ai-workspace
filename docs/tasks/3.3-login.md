# Task 3.3 — Login

## Objective

Turn credentials into an authenticated user, with one indistinguishable failure
for every way it can go wrong.

## Context

3.4 built the pieces: `verify_password` that never raises, `verify_absent_user`
for the no-user branch, `needs_rehash` for upgrading cost. 3.2 made registration
enumeration-safe; sign-in has to keep the same property or the pair leaks what
neither does alone.

**What the endpoint returns is task 3.5.** This one authenticates and returns the
profile; the session and its tokens come next.

## Implementation steps

1. `AuthService.authenticate` — look up, verify, and return the user or `None`.
2. The no-user branch calls `verify_absent_user`, so both paths cost the same.
3. One `AuthenticationError` for a wrong address, a wrong password, an
   identity-provider account with no password, and a disabled account.
4. Rehash on success when parameters have moved.
5. `POST /auth/login`.
6. Tests, including a timing comparison and that every failure looks the same.

**Excluded:** tokens and sessions (3.5), logout (3.6), rate limiting (10.5).

## Acceptance criteria

- Correct credentials return the profile, and never the password hash.
- Wrong password, unknown address, no-password account and disabled account all
  return the same status, code and message.
- The unknown-address path costs the same order of time as the wrong-password one.
- A password stored with weaker parameters is upgraded on a successful sign-in,
  and the user can still sign in afterwards.
- Sign-in is case-insensitive in the address.
- `scripts/check.sh` passes.

## Tests

Unit for the failure shape; integration for the database paths and the rehash.

### Deviations
- **`is_active` is checked *after* the password, not before.** Checking it first
  would let a disabled account answer faster than a wrong password, which
  reveals the address exists — the opposite of the point.
- **`LoginRequest.password` does not use the 3.4 policy type.** An existing
  password predates any policy change; refusing to *check* it would lock people
  out of their own accounts. Only registration enforces the policy.
- **The distinct reason goes to the log, not the response.** `no_user`,
  `bad_password` and `inactive` are all recorded with the request id; the client
  gets one sentence.
- **A test bug worth recording.** The first version banned the word "password"
  anywhere in the failure message, which would have rejected "that email address
  and password do not match" — a perfectly good generic message. It now checks
  for phrases that name a *cause*.

### Known limitations
- No rate limiting, and each attempt costs ~50 ms of Argon2 (ADR-017). Sign-in is
  the endpoint that most needs 10.5.
- No lockout or failed-attempt counter; both belong with rate limiting.
- Returns a profile, not a session — task 3.5. Nothing is signed in yet in any
  useful sense.
