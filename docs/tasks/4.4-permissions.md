# Task 4.4 — Permissions

## Objective

Make the permission table something HTTP handlers depend on, rather than
something they could remember to consult.

## Context

4.3 built `TenantScope.require` and nothing calls it. A permission check written
inside a handler body is a check that the next handler can omit; a dependency is
one that cannot be, because the route will not resolve without it.

The organisation is identified by a slug in the path. That makes the tenant
visible in every URL and in every log line, and it means the scope is resolved
by the framework before a handler runs.

## Implementation steps

1. `TenantScopeDep` — resolves the scope from the path slug and the principal.
2. `require_permission(...)` — a dependency factory returning a scope that has
   already been checked.
3. Organisation endpoints: create, list mine, read one.
4. Member listing, guarded by `member:read`.
5. Tests: every endpoint refuses a non-member, and refuses a member lacking the
   permission.

**Excluded:** switching (4.5), role changes and removal over HTTP (4.6), the
systematic isolation sweep (4.7).

## Acceptance criteria

- A signed-out caller gets 401 from every organisation endpoint.
- A non-member gets 404 — the same as a slug that does not exist.
- A member without the permission gets 403 naming what they need.
- Creating an organisation returns it and makes the caller its owner.
- Listing returns only the caller's own organisations.
- `scripts/check.sh` passes.

## Outcome — completed 2026-09-13

Four organisation endpoints, each resolving its tenant through
`TenantScopeDep` and, where it needs one, `require_permission(...)`.

```
POST /api/v1/organizations                                 201, caller becomes owner
GET  /api/v1/organizations                                 the caller's own only
GET  /api/v1/organizations/{organization_slug}             organization:read
GET  /api/v1/organizations/{organization_slug}/members     member:read
```

| Check | Result |
| --- | --- |
| signed-out caller, all four endpoints | 401 |
| **non-member vs. missing slug** | both 404, byte-identical body |
| a viewer hitting a route needing `organization:delete` | 403 naming the permission |
| create returns the organisation and an owner membership | pass |
| listing excludes organisations the caller does not belong to | pass |
| a malformed slug | 422 before any database lookup |
| unit / integration | 181 / 103 pass |

### Deviations
- **`require_permission` returns the `Depends` itself** rather than a function to
  wrap in one. Written `Annotated[TenantScope, require_permission(X)]`, the
  permission sits in the signature and cannot be dropped without changing the
  handler's parameters.
- **The 403 path is exercised through a test-only route.** Every endpoint here
  needs only permissions all four roles hold, so without a restricted route
  mounted the refusal path would have gone unproven until 4.6.
- **The slug is validated in the path type, not the service.** A malformed slug
  is a malformed URL; rejecting it at the boundary keeps unlookupable strings out
  of the query log.

### Known limitations
- No pagination on either list. Both are bounded by memberships today; documents
  in phase 5 will not be.
- Member listing exposes email addresses to any member. Right for a workspace,
  worth revisiting if viewer becomes a guest-like role.
