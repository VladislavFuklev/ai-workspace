# Task 2.2 — Configuration

## Objective

Close the configuration gaps 2.1 exposed: what the app needs to know about itself
and its callers, rather than only about its backing services.

## Context

**This task overlaps 0.5**, which delivered a typed, validated `Settings` with
secrets as `SecretStr`, no working defaults, and 18 tests. Redoing it would be
churn. What 0.5 did not model, because nothing needed it yet:

- CORS origins — the web app is on a different port and will be on a different
  host in production.
- Service identity and the API prefix, currently hard-coded in `create_app`.
- Per-environment behaviour beyond `debug`, chosen in one place rather than by
  scattered `if environment ==` checks.

## Implementation steps

1. Add `cors_origins`, `service_name`, `api_prefix`, and a request-body size limit
   to `Settings`, parsed and validated.
2. Wire CORS into `create_app` from settings; no origins in production unless
   configured.
3. Replace the literals in `create_app` with settings.
4. Guard rails: refuse a wildcard CORS origin together with credentials in
   production — a combination browsers reject and that hides a real misconfiguration.
5. Extend `.env.example`.
6. Tests for parsing, the production guard, and the CORS headers actually sent.

## Acceptance criteria

- A comma-separated origin list parses into a validated list.
- A wildcard origin in production fails startup with a message naming the field.
- A permitted origin receives `access-control-allow-origin`; a foreign one does not.
- No literal service name or prefix left in `create_app`.
- `scripts/check.sh` passes.

### Deviations
- **Overlapped 0.5 and was scoped to the gap**, as 1.3 was to 0.8.
- **`NoDecode` is required on the list field.** The claim in the first version's
  comment — that pydantic-settings splits a bare string for a list — is false: the
  env source JSON-decodes complex fields *before* validators run, so
  `CORS_ORIGINS=a,b` raised a `SettingsError` rather than parsing. Found by running
  it, not by reading.
- **No origins means no middleware**, rather than middleware with an empty list.
  A misconfiguration then fails visibly instead of half-working.

### Known limitations
- `max_request_body_bytes` is configured but not yet enforced; task 5.3 applies it.
- `api_prefix` is configured but unused until 2.9.
