# Task 5.1 — File storage abstraction

## Objective

One way for the product to put a file somewhere and get it back, with the tenant
in the key, so isolation survives into storage.

## Context

MinIO runs in Compose and is configured but unused. What matters here is not
"wrap boto3" but the shape of the interface: what a caller must hold to write a
file (a `TenantScope`, not an organisation id), what a key looks like, and what
happens when the store is unreachable.

The key layout is the decision that cannot be changed later without a migration:
every object must be attributable to one organisation from its key alone, so a
mistake is visible in a bucket listing rather than only in the database.

## Implementation steps

1. A `Storage` protocol: put, get, delete, presigned URL — taking a scope and a
   logical name, never a raw path from the caller.
2. An S3/MinIO implementation, and a local one for tests that never touches the
   network.
3. Keys as `org/{organization_id}/{kind}/{uuid}{ext}`, generated here, never
   supplied by the caller.
4. Content type and size limits enforced on write, not trusted from the client.
5. Health: the readiness probe should say when storage is unreachable.

**Excluded:** upload UI (5.2), the upload endpoint (5.3), extraction (5.4).

## Acceptance criteria

- A caller cannot write outside their organisation's prefix — there is no
  argument that would let them.
- A traversal attempt in a filename cannot escape the key layout.
- An oversized or wrong-typed object is refused before it is stored.
- The store being down is an error the API reports, not a hang.
- `scripts/check.sh` passes, with the storage tests running offline.

## Tests

Unit against the local implementation; one integration test against MinIO,
skipped when it is not running, in the manner of the Redis fixture.

## Documentation

`docs/ARCHITECTURE.md`, `PROJECT_STATE.md`, `CHANGELOG.md`, `ROADMAP.md`, this
file, and an ADR for the key layout.

## Outcome — completed 2026-09-15

`core/storage/`: the rules in `base.py`, S3/MinIO in `s3.py`, a dictionary in
`memory.py`. Keys are `org/{organization_id}/{kind}/{uuid}{extension}` (ADR-022),
built from a `TenantScope` and never from anything the caller sends.

### Deviations
- **An abstract base class, not the `Protocol` the plan named.** The point is not
  that several classes share method names, it is that nobody can store outside
  their own prefix. The public methods hold the checks and subclasses implement
  only `_put`/`_get`/`_delete`/`_presigned_url`, so a second implementation
  cannot satisfy the type while forgetting a rule.
- **`aioboto3`, not `boto3` in a thread pool.** The stack is async throughout;
  `types-aioboto3[s3]` keeps it typed under `disallow_any_unimported`. Its
  config type is `AioConfig`, not botocore's `Config` — mypy caught that.
- **`InMemoryStorage` is in `src`, not in the tests.** It inherits the same base,
  so it enforces the same rules; a test that passes against it is testing the
  rules and not a stand-in that agrees with them. It is also what makes the unit
  suite run with no network.
- **CI runs MinIO from a plain `docker run`.** A service container cannot
  override an image's command, and MinIO needs `server /data`. The two steps that
  provision the runner are marked `(CI only)` and skipped by
  `scripts/check-ci.sh`, which must not start containers on a machine where the
  compose stack already holds port 9000 with different credentials.
- **The bucket is created in CI rather than assumed.** The readiness probe
  asserts it exists, so assuming it would make that assertion untested.

### Known limitations
- `put` takes `bytes`, so a 25 MB upload is 25 MB in memory. Fine at this limit;
  streaming is the change to make if the limit ever rises.
- Nothing calls this yet — 5.3 is the upload endpoint. What exists is the
  interface, its rules and its two implementations.
- A readiness probe against a hanging store takes up to its 2 s timeout, because
  botocore retries underneath it. Bounded, but not instant.
- `scripts/check-ci.sh` still reports `Migrate` and the integration run as
  failures locally: the CI environment points at `ci:ci@localhost:5432`, which no
  developer machine has. Pre-existing, and worth fixing when 13.8 revisits CI.
- No lifecycle rules on the bucket, so deleted documents leave nothing behind
  only because `delete` is called. An orphan sweep belongs with 5.5.
