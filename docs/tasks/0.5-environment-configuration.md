# Task 0.5 — Environment configuration

## Objective

One typed, validated configuration surface per app, so a misconfigured environment
fails at startup with a clear message instead of at the first request.

## Context

`.env.example` exists but is read only by Docker Compose (task 0.3). Neither app
reads configuration at all yet. ADR-007 noted a trap this task must resolve: host
processes reach services on `localhost` with mapped ports, containers reach them by
service name on the internal port — the same setting has two correct values.

## Prerequisites

- Tasks 0.3 and 0.4 complete.

## Implementation steps

1. **API** — a settings object in `ai_workspace_api/core` using `pydantic-settings`,
   instantiated once and injected. Validate at import/startup so a bad value stops
   the process. No `os.environ` reads anywhere else.
2. Model the values needed so far: database URL, Redis URL, S3 endpoint/bucket/
   credentials, environment name, log level. No secret gets a working default.
3. **Web** — validate the public environment at build time (Zod), and keep the
   server/client split explicit so no secret can reach the browser bundle.
4. Reconcile the two connection contexts from ADR-007 — decide whether `.env`
   carries host values with container overrides in compose, or the reverse, and
   document it.
5. Extend `.env.example` to cover everything both apps read, grouped and commented.
6. Make a missing required variable produce a message naming the variable.

## Acceptance criteria

- Starting the API with a required variable unset fails immediately, naming it.
- Starting it with a malformed value (a non-URL database URL) fails with a message
  identifying the field.
- No `os.environ` or `process.env` read outside the two configuration modules,
  verified by grep.
- No secret is readable from a client component in the web app.
- The same `.env` works for host-run apps and for the `api` compose profile, or the
  difference is explicit and documented.
- `scripts/check.sh` still passes.

## Tests

Unit tests for the settings object: a valid environment, a missing required
variable, and a malformed value. These are the first tests in the repository, so
this task also establishes where API tests live and how they run — but not the
wider test tooling, which is phase 12.

### Deviations
1. **`@next/env` added as an explicit dependency.** It is a transitive dependency of
   `next`, and pnpm's strict layout makes it unresolvable from our code. Declared it
   rather than hand-rolling a `.env` parser.
2. **`forceReload: true` is required.** Next.js has already called `loadEnvConfig`
   for the app directory by the time `next.config.ts` runs; without the flag the
   second call returns the cached result and silently does nothing. Found by the
   build still failing after the "fix".
3. **Tests build `Settings` from environment variables, not constructor kwargs.**
   The first version splatted a `dict[str, str]`, which strict mypy rejects against
   DSN and `SecretStr` fields. Rewriting it around `monkeypatch` removed the type
   errors *and* exercises the real production path.
4. **No `env.server.ts` yet.** There is no server-only secret in the web app; an
   empty module would be filler. The split is documented, and the guard
   (`import "server-only"`) lands with the first secret in phase 3.
5. **pytest wired into `scripts/check.sh`.** A gate that passes while tests fail is
   worth less than the two seconds it saves. Phase 12 still owns test tooling.

### Known limitations
- `POSTGRES_*` and `DATABASE_URL` are separate and must agree — see ADR-013.
- `env` in the web app has no consumer yet, so nothing is inlined into the client
  bundle; the API client (1.7) will be the first.
- The dev image bakes source at build time, so API source changes need a rebuild.
- Secrets are plaintext in `.env`; a secret manager is phase 13.
