# Task 3.8 — OAuth-ready architecture

## Objective

The seam an identity provider plugs into, without integrating one.

## Context

`password_hash` has been nullable since 3.1 for exactly this. What is missing is
the table linking a provider's idea of a person to ours, and the rule for what
happens when a provider's email matches an existing account.

Integrating a real provider is out of scope: it needs client credentials, a
redirect URI, and a decision about which providers — none of which this task can
answer alone.

## Implementation steps

1. An `identities` table: provider, the provider's subject id, linked user.
   Unique on `(provider, subject)`.
2. A service that finds or creates a user from a verified provider profile.
3. Decide the account-linking rule and record it.
4. Tests for linking, re-linking and the collision case.

**Excluded:** any provider's OAuth flow, client credentials, redirect handling.

## Acceptance criteria

- A first sign-in with a provider creates a user with no password.
- A second sign-in with the same provider identity returns the same user.
- The same subject under a different provider is a different identity.
- A provider email matching an existing account does **not** silently link.
- An identity cannot be attached to two users.
- `scripts/check.sh` passes.

### Deviations
- **The subject is the key, not the email.** An email can be reassigned to a
  different person after an employee leaves; linking on it would hand the new
  holder the old one's account.
- **`email_verified` is recorded but is not sufficient** to link to an existing
  account. It proves the provider believes the address, not that the person
  controls the account here.
- **No provider integrated.** Client credentials, redirect URIs and the choice of
  providers are decisions this task cannot make alone. The seam is what was
  asked for and what is here.

### Known limitations
- No unlink, and no guard against removing the only sign-in method — a user with
  one identity and no password could otherwise lock themselves out.
- The provider enum is fixed at three; adding one is a migration.
- Nothing exposes these over HTTP yet; the routes arrive with the OAuth flow.
