# Task 3.10 — Protected routes

## Objective

Keep signed-out visitors out of the product, verify it on the server, and put
them back where they were going.

## Context

3.9 built the screens; nothing yet stops anyone opening `/workspace`. The session
cookie is `HttpOnly`, so the browser cannot read it — the check has to be on the
server, and the web app has no signing key to verify a token itself.

## Implementation steps

1. `getServerUser` — a Server Component asks the API `/auth/me`, forwarding the
   incoming cookies.
2. The `(app)` layout redirects when that returns nothing.
3. Middleware redirects on a *missing* cookie, as a fast path only.
4. Remember the destination in `?next=` and return there after signing in.
5. Sign-out in the header, clearing the query cache and refreshing the route.

## Acceptance criteria

- A signed-out visitor is redirected from every protected route, in both locales.
- The destination is preserved and honoured after signing in.
- Public routes stay open.
- A signed-in visitor sees the page, their name and a sign-out control.
- **A forged cookie passes the middleware and is still rejected**, proving the
  server check is the real guard.
- `next` cannot redirect off-site.
- `scripts/check.sh` passes.

## Tests

12.8 owns end-to-end. Verified against running API and web servers.

### Deviations
- **Two layers, and only one is the guard.** The middleware asks whether a cookie
  exists, which proves nothing; it exists so a signed-out visitor is redirected
  before a page is rendered and discarded. The layout asks the API. The forged
  cookie test is what shows the difference is real.
- **`next/navigation`'s `redirect`, not next-intl's.** The locale-aware one did
  not narrow the type — the compiler could not see that nothing runs after it,
  and the alternative was a non-null assertion, which is the cast the frontend
  rules forbid. The locale is already in hand, so building the path is free.
- **`next` is validated before use.** A path that does not start with a single
  `/` is ignored; `//evil.test` is an open redirect, and an open redirect on a
  sign-in page is a credible phishing step.
- **Sign-out clears the query cache and calls `router.refresh()`.** The layout is
  a Server Component, so its copy of the user survives a client navigation
  otherwise.

### Known limitations
- The layout's own redirect drops `?next=`; only the middleware path preserves
  it, so an expired session loses the destination. Worth fixing when session
  expiry becomes visible in the UI.
- `getServerUser` treats an unreachable API as signed out, which sends people to
  sign-in during an outage rather than showing them an error.
- The protected list in the middleware is a literal array that has to be kept in
  step with `(app)`. A route added there without updating it loses only the fast
  path, not the guard.
- No end-to-end test until 12.8; verified by hand against running servers.
