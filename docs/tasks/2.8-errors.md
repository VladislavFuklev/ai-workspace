# Task 2.8 — Exception handling

## Objective

Every failure comes back in one envelope, and none of them tells the caller
anything about the internals.

## Context

The shape is already fixed: `apps/web/src/lib/api/errors.ts` (task 1.7) parses
`code`, `message` and a `detail` array of `{field, message}`, and the form layer
(1.9) maps that detail back onto its fields. The API has to produce what the
client already reads.

## Implementation steps

1. `core/errors.py` — domain exceptions with a stable `code` and a status. A
   service raises one of these; nothing in the domain raises `HTTPException`.
2. `schemas/errors.py` — the envelope, including a `request_id` to quote.
3. Handlers for domain errors, request validation, Starlette HTTP errors, and
   anything unhandled.
4. Reshape FastAPI's own 422 into the same envelope.
5. The unhandled handler logs the traceback and returns a generic sentence.

## Acceptance criteria

- Each domain error maps to its status and code, with a `request_id`.
- A 422 carries `{field, message}` entries the web form can use.
- An unhandled error leaks no credential, host, exception type or traceback.
- The `request_id` in the body matches the `X-Request-ID` header.
- An unmatched route and a wrong method use the same envelope.
- `scripts/check.sh` passes.

## Tests

Unit, against routes that fail in each way a real handler can.

### Deviations
- **`RequestContextMiddleware` rewritten as pure ASGI.** `BaseHTTPMiddleware` runs
  the app in a task group and re-raises through it, which is why an unhandled
  error behaved differently under test than against a real server. It also buffers
  streaming responses, which would matter from phase 7. The rewrite is the fix and
  an improvement.
- **A real defect found by running the server:** the 500 response carried
  `request_id: null`. Starlette's `ServerErrorMiddleware` sits outside the request
  middleware, so the context variable is already reset when it handles the error —
  exactly the response where a user most needs a reference. The id now also lives
  on the ASGI state, and error responses set the header themselves.
- **No `assert` for type narrowing.** Asserts are stripped under `python -O`; a
  stripped narrowing turns a wrong registration into an `AttributeError` in
  production. Each handler narrows with `isinstance` and falls through.
- **Warnings now fail the suite** (`-W error`). Two deprecated Starlette status
  constants were sitting in the code; a warning nobody fails on becomes a break
  later.

### Known limitations
- `handle_domain_error` logs at info. Right for expected failures, but a spike in
  403s is worth alerting on — that belongs with metrics (11.6).
- No error-tracking integration; 11.7.
