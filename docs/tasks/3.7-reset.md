# Task 3.7 — Password reset

## Objective

A reset flow that is safe to expose: single-use tokens, short expiry, no
enumeration, and every existing session ended when the password changes.

## Context

There is still no email delivery, so the token cannot reach a user. The design,
the storage and the endpoints are buildable now; the delivery is one call in the
request handler when it exists.

Deliberately **no development backdoor** that returns or logs the token. A
convenience like that is exactly what survives into production.

## Implementation steps

1. `password_reset_tokens` table: hashed token, expiry, single-use marker.
2. Request endpoint — always the same answer, whether or not the address exists.
3. Confirm endpoint — validate, apply the 3.4 policy, set the new hash.
4. **Revoke every session on success.** A reset is what someone does when they
   think their account is compromised; leaving the attacker's session alive
   defeats the point.
5. Invalidate all outstanding reset tokens for that user too.

## Acceptance criteria

- Requesting for an unknown address answers exactly as for a known one.
- The raw token is not stored.
- A token works once; the second attempt fails.
- An expired token fails.
- A token for a different user cannot be used.
- The new password must satisfy the policy.
- After a reset, every session is revoked and the old password no longer works.
- `scripts/check.sh` passes.

## Tests

Integration for the lifecycle; unit for the token primitives.

### Deviations
- **No development mode that returns or logs the token.** It is the obvious
  convenience and exactly the kind that survives into production, where it is an
  account-takeover API. Tests call the service directly instead.
- **Requesting a second link invalidates the first.** Not required, but a stale
  link sitting in an inbox is a standing key, and only one should ever work.
- **Renamed a constant rather than silencing Ruff.** `S105` fired on
  `INVALID_TOKEN` as a hardcoded password. Renaming to `INVALID_LINK_MESSAGE`
  keeps the rule sharp for the cases where it is right.

### Known limitations
- **The flow cannot be completed by a user**: nothing sends the token. One call
  in the request handler when email delivery exists.
- No rate limit on the request endpoint, so it can be used to send mail
  repeatedly once delivery exists. 10.5.
- Used and expired rows are never swept; a job for 5.7.
