# Task 0.6 — CI baseline

## Objective

Run the quality gate on every push and pull request, so a broken change is caught
before review rather than after merge.

## Context

`scripts/check.sh` runs format, lint, types and tests for both workspaces in ~3s
locally (task 0.4, extended in 0.5). CI's job is to run the same thing on a clean
machine — not to define a second, divergent set of checks.

## Prerequisites

- Tasks 0.4 and 0.5 complete.

## Implementation steps

1. `.github/workflows/ci.yml` — trigger on push to `main` and on pull requests.
2. Separate jobs for web and API (ADR-005: independent dependency graphs), so a
   failure names the ecosystem and the two run in parallel.
3. Pin Node 22 from `.nvmrc`, pnpm from `packageManager`, Python from
   `.python-version`. Never resolve "latest" in CI.
4. Cache the pnpm store and the uv cache, keyed on the lockfiles.
5. Install with `--frozen-lockfile` / `--locked`: CI must fail on a stale lockfile
   rather than quietly resolving something new.
6. Provide the environment the checks need. Decide whether CI gets a `.env`, a
   dedicated env block, or defaults — and whether any job needs live services.
7. Add a build job for the web app if it is not already covered.

## Acceptance criteria

- The workflow runs on push and pull request and is green on the current `main`.
- A deliberately broken commit (a lint error) fails CI, and the log names the file.
- A stale lockfile fails the install step.
- Total wall-clock under about five minutes.
- No secret is required for CI to pass.
- CI runs the same `scripts/check.sh` as the pre-commit hook — no divergent copy.

## Tests

Verification is the workflow itself: one green run and one deliberately red run,
both recorded in the outcome.

### Deviations
- **CI runs the workspace commands directly, not `scripts/check.sh`.** The script
  is one process with one exit code; separate steps make GitHub show which check
  failed without opening the log, and let the two ecosystems run in parallel. The
  commands are identical — the risk is drift, so any new check must be added in
  both places.
- **No live services.** Nothing in the current suite opens a connection; the API
  env block is syntactically valid but points nowhere. Service containers arrive
  when integration tests do (12.5).

### Known limitations
- **Not yet observed green on GitHub** — the commits are local. Verified by running
  each job's exact commands locally without a `.env`.
- Duplication between `ci.yml` and `scripts/check.sh` must be kept in step.
