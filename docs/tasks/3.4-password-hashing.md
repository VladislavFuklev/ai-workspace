# Task 3.4 — Password hashing

## Objective

One place that turns a password into a stored hash and back into a yes/no, with
an algorithm chosen deliberately and a path to change it.

## Context

Brought forward ahead of 3.2 and 3.3: registration cannot be written before this
exists without handling a plaintext password insecurely, even briefly.

`password_hash` is a nullable 255-character column (3.1). An identity-provider
account has none, so every verification path must handle absence without leaking
which case it hit.

## Implementation steps

1. Argon2id via `argon2-cffi`, behind a small interface — the algorithm is a
   detail, and OWASP's recommendation changes.
2. `verify` returns a boolean and never raises for a wrong password; a malformed
   or absent hash is a failure, not an exception reaching a handler.
3. Rehash-on-verify when parameters change, so cost rises without asking anyone
   to reset a password.
4. Constant-time behaviour for an unknown user: verify against a dummy hash so
   the response time does not reveal whether an address is registered.
5. Password policy as a schema, checked before hashing.
6. Tests, including that the same password hashes differently twice.

**Excluded:** any endpoint (3.2, 3.3), tokens (3.5), reset flow (3.7).

## Acceptance criteria

- Hashing the same password twice gives different strings.
- A correct password verifies; a wrong one does not.
- A `None` hash verifies to false without raising.
- A malformed hash verifies to false without raising.
- A hash produced with weaker parameters is reported as needing a rehash.
- Verifying against a missing user costs about the same as against a real one.
- The policy rejects short and common passwords with a message naming the reason.
- `scripts/check.sh` passes.

## Tests

Unit only — no database involved.

### Deviations
- **The forbidden-password list was exact-match and nearly useless.** A test
  caught `password1234` passing. It now strips trailing digits and punctuation
  and compares the root, which is the shape people pick when told to add a
  number — `Welcome2026!` and `qwerty123456` are caught too, while a passphrase
  merely containing a common word is not.
- **`verify_absent_user` is a separate function**, not a flag on `verify_password`.
  A caller has to think about the no-user branch, and the name says what it is
  for.
- **The dummy hash is computed once at import.** Computing it per call would be
  its own timing signal.
- **The timing test asserts an order of magnitude**, not a constant time. A tight
  bound would be flaky on a shared runner, and the failure it exists to catch —
  a missing dummy verification — is a factor of hundreds. Verified stable across
  five runs and confirmed to fail when the dummy is removed.

### Known limitations
- The common-password check is a small root list, not a breach corpus. A real
  check belongs behind a service; worth revisiting at 3.7.
- Argon2 timing is not constant across inputs of very different lengths; the
  policy's 128-character cap bounds it.
- ~50 ms per verification makes sign-in a denial-of-service target until rate
  limiting lands (10.5). Recorded in ADR-017.
