# Task 1.8 — Query and cache architecture

## Objective

Server state handled by TanStack Query with a policy chosen for this product, and
query keys that an invalidation cannot miss.

## Context

1.7 gave the app a transport that classifies its own errors. This decides what the
cache does with them.

## Implementation steps

1. `queryKeys` — a hierarchy, built centrally, never typed at a call site.
2. `createQueryClient` — retry driven by `ApiError.isRetryable`, a real
   `staleTime`, no mutation retries.
3. `QueryProvider` creating the client in state, not at module scope.
4. Mount it in `(app)/layout.tsx`.

## Acceptance criteria

- 4xx and parse failures are not retried; 5xx, timeout and network are.
- Retries stop at the configured ceiling.
- Mutations never retry.
- Keys nest so a parent invalidation covers its children.
- `scripts/check.sh` passes.

## Tests

12.1 owns the runner. Verified through a temporary route handler exercising the
retry predicate directly.

### Deviations
- **The client is created in `useState`, not at module scope.** A module-level
  QueryClient is shared across requests on the server, which would leak one
  user's cached data into another's render.
- **`refetchOnWindowFocus` is off.** Right for a dashboard, wrong while someone is
  reading a document; queries that want it can opt in.

### Known limitations
- No query or mutation uses this yet — the API has no endpoints until 2.1.
- No SSR hydration (`HydrationBoundary`). Worth revisiting when a route actually
  prefetches.
- Devtools not installed; add when there is cached data to inspect.
