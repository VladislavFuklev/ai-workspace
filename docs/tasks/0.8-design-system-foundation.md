# Task 0.8 — Design system foundation

## Objective

A defined visual language — colour, type, spacing, radii, elevation — expressed as
Tailwind 4 theme tokens, so phase 1 composes from a system instead of inventing
values per screen.

## Context

`apps/web/src/app/globals.css` is a bare `@import "tailwindcss"`. Tailwind 4
configures its theme in CSS via `@theme`, not a JS config file — check the
installed Tailwind docs before writing it.

The brief is explicit that the product must not look like a generated dashboard.
The `ui-review` skill lists what that rules out and what it requires.

## Prerequisites

- Task 0.7 complete.

## Implementation steps

1. Define the token set in `globals.css` under `@theme`: a neutral ramp, one
   accent, semantic colours for success/warning/danger, and surface/border roles.
2. Light and dark values, driven by a `data-theme` attribute plus
   `prefers-color-scheme`. The switching UI is task 1.5; the tokens are here.
3. Type scale — family, sizes, line heights, weights. At most three sizes per
   screen is the rule the scale should make easy.
4. Spacing scale, radii, and one or two elevation levels. Restraint over range.
5. Verify every text/background pairing against WCAG AA (4.5:1 body, 3:1 large
   and UI boundaries) in both themes, and record the measured ratios.
6. A single page rendering the tokens, so the system is inspectable. Keep it out
   of the product surface.

## Acceptance criteria

- Every token is defined once, in `@theme`, and no colour is hardcoded elsewhere.
- Both themes are complete: no token defined only inside a media query.
- Measured contrast meets AA for every pairing, recorded in the outcome.
- The token page renders correctly at 375px, 768px and desktop.
- `scripts/check.sh` passes.

## Tests

No unit tests. Verification is the contrast measurements and a `ui-review` pass at
the three breakpoints.

### Deviations
- **The first version of `/design` composed class names (`bg-${token}`) and would
  have rendered unstyled.** Tailwind scans source as text, so those produce no CSS
  — and it builds and typechecks cleanly. Caught by grepping the built stylesheet
  for the utilities the page claims to use: `shadow-md`, `size-12`, `bg-bg` and
  `bg-success-subtle` were all absent. Rewritten with full class strings.
- **Two palette values were typos** — `#e962eb` (magenta, meant as a grey) and
  `#182votes` (not a colour). The contrast script's hex-only regex skipped them
  silently, so it now rejects any `--color-*` that is not a 6-digit hex.
- **`border-strong` failed AA in both themes** at first (1.89:1 and 2.42:1 against
  a 3:1 floor). Darkened to `#8a929e` and lightened to `#636e7d`.
- **Contrast added to CI as well as `check.sh`**, since the two must not diverge.

### Known limitations
- Visual review is limited to markup and generated CSS: no browser automation
  until Playwright (12.8), so the responsive and focus behaviour of `/design` is
  reasoned from its classes, not observed. Worth a human look.
- No theme switcher yet — `data-theme` has to be set by hand. Task 1.5.
- `/design` is reachable in production builds. Task 1.10 decides its fate.
