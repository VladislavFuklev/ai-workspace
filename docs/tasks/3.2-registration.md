# Task 3.2 — Registration

## Objective

Create an account from an email address, a password and a display name, without
the response revealing whether the address was already registered.

## Context

3.1 gave the table and repository, 3.4 the hashing and policy. The open question
this task has to answer is enumeration: a registration endpoint that says "that
address is taken" hands an attacker a membership oracle for any list of
addresses.

The usual resolution is to answer identically either way and send an email — a
welcome to a new address, a "someone tried to register with your address" to an
existing one. **This project has no email delivery yet**, so only the first half
is available. See the decision recorded in the outcome.

## Implementation steps

1. `schemas/auth.py` — request with `EmailStr`, the 3.4 `Password`, and a display
   name; a response carrying no more than the client needs.
2. `services/auth.py` — the rule layer: normalise, check, hash, create. It owns
   the transaction boundary; the repository does not commit (2.3).
3. `api/v1/routes/auth.py` — `POST /auth/register`, mounted on the v1 router.
4. Identical response and status whether or not the address exists.
5. Tests, including that the two cases are indistinguishable from outside.

**Excluded:** sign-in (3.3), tokens and sessions (3.5), email verification and
delivery, rate limiting (10.5).

## Acceptance criteria

- A new address creates a user with a hashed password and returns 201.
- A duplicate address returns the same status and body as a new one.
- No user is created for the duplicate, and the existing one is untouched.
- The password never appears in the response or the logs.
- A weak password is rejected with a field-level error the web form can place.
- A malformed address is rejected the same way.
- Email is stored normalised whatever case was submitted.
- `scripts/check.sh` passes.

## Tests

Unit for schema validation; integration for the endpoint against a real database.

## Outcome — completed 2026-09-13

`POST /api/v1/auth/register`. Schemas, an `AuthService` owning the transaction,
and a route that ignores the service's return value on purpose.

| Check | Result |
| --- | --- |
| a new address creates a user; email stored normalised from `Fresh@Example.com` | pass |
| the stored password is Argon2id and verifies; plaintext appears nowhere | pass |
| **duplicate is indistinguishable** — same status and body, including different case | pass |
| a duplicate creates nothing and leaves the password and name untouched | pass |
| 7 invalid inputs rejected 422 with the field named | pass |
| the submitted password is never echoed | pass |
| unit / integration | 131 / 18 pass |

### Deviations
- **The route discards what the service returns.** Branching on it is exactly the
  leak the endpoint exists to avoid, so the service reports "existing" for
  logging and the future email, and the handler answers the same either way.
- **Registration is only half-designed without email delivery** (ADR-018). A
  duplicate is currently silently inert, so someone who forgot they had an
  account gets no feedback. Accepted deliberately; the completing half is the
  notification.
- **Integration tests bind the app's session to an outer transaction** and roll it
  back. The service commits, so without that each run would leave users behind and
  the next would collide on the unique index.
- **Two test bugs, not code bugs.** The payload helper took `email` positionally
  and as an override — a `TypeError` in the parametrised case. And a test still
  asserted the v1 router was empty; it now reads the OpenAPI document, since
  FastAPI 0.141 keeps an included router as one opaque entry (the third time that
  has come up).

### Known limitations
- No email verification, so `is_verified` never becomes true.
- No rate limiting, and this endpoint does Argon2 work per call — ADR-017 and
  ADR-018 both point at 10.5.
- Display name is trimmed but not otherwise validated; a name of only punctuation
  is accepted.
