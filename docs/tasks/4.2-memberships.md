# Task 4.2 — Memberships

## Objective

Link users to organisations, and establish the one enforced path every
tenant-scoped query must go through.

## Context

4.1 gave the boundary; nothing crosses it yet. The `backend-quality` skill is
explicit about the shape this has to take: a `WHERE organization_id = ...`
remembered in forty places is a cross-tenant leak waiting for the one place it
is forgotten. This task builds the alternative before there is anything to
forget it in.

## Implementation steps

1. `memberships` table: user, organisation, role, unique on the pair.
2. Creating an organisation makes its creator the owner, in one transaction.
3. A `TenantScope` — a verified (user, organisation) pair that a repository
   requires in order to be constructed at all.
4. Repository for listing a user's organisations and resolving a scope.

**Excluded:** what roles *mean* (4.3), switching (4.5), endpoints (4.5, 4.6).

## Acceptance criteria

- Creating an organisation produces exactly one membership, with the owner role.
- A user cannot be added to the same organisation twice.
- Deleting a user or an organisation removes the membership.
- Resolving a scope for a non-member fails, and fails the same way as a
  non-existent organisation.
- A scope cannot be constructed without a membership having been verified.
- `scripts/check.sh` passes.

### Deviations
- **`TenantScope` is a type, not a uuid parameter** (ADR-021). A bare id can be
  passed from anywhere including a request body; a scope can only come from a
  verified membership.
- **Creating an organisation and its first membership is one transaction.** An
  organisation with no members is unreachable by everyone, including its creator,
  and nothing in the product could repair it.
- **`get_by_slug` is one query, not two.** "Find the organisation, then check
  membership" lets a caller act on the first result before the second answers,
  which is the shape of an isolation bug.
- **A non-member gets 404, not 403.** Saying "you are not a member of this
  organisation" confirms it exists, and a URL becomes a way to enumerate tenants.

### Known limitations
- No tenant-scoped repository uses `TenantScope` yet — documents in phase 5 are
  the first. Until then the type is a promise the compiler cannot check.
- No invitations; the only way into an organisation is to create it (4.4/4.5).
- Nothing stops the last owner leaving, which would strand the organisation.
  That belongs with 4.3, where roles gain meaning.
