# Task 3.5 — Access and refresh token strategy

## Objective

Turn a successful sign-in into a session the browser carries automatically, that
can be revoked, and whose theft is detectable.

## Context

3.3 returns a profile and nothing is actually signed in. The web client already
sends `credentials: "include"` (1.7), so cookies are the shape it expects.

## Implementation steps

1. A `sessions` table: the refresh token stored **hashed**, a family id, expiry,
   revocation.
2. Short-lived access token (JWT) so most requests need no database read;
   long-lived opaque refresh token so revocation is possible.
3. Both in `HttpOnly` cookies. The refresh cookie is scoped to the refresh path,
   so it is not sent with every request.
4. **Rotation with reuse detection**: refreshing issues a new token and retires
   the old one. Presenting a retired token revokes the whole family — that is a
   stolen token being replayed.
5. Settings for the signing secret and lifetimes, with a production guard on
   insecure cookies.
6. `POST /auth/refresh`, and sign-in issues the pair.

**Excluded:** logout and revoke-all (3.6), reset (3.7), the frontend (3.9, 3.10).

## Acceptance criteria

- Sign-in sets both cookies, `HttpOnly`, `SameSite=Lax`, and `Secure` outside local.
- The refresh cookie's `Path` is the refresh endpoint, not `/`.
- The raw refresh token is not in the database.
- Refreshing returns a new pair and retires the old token.
- Reusing a retired token revokes every session in that family.
- An expired or unknown refresh token is rejected.
- An access token cannot be used as a refresh token.
- A tampered access token is rejected.
- Insecure cookies are refused at startup in production.
- `scripts/check.sh` passes.

Unit for token encoding and settings; integration for the session lifecycle.

### Deviations
- **A minimum length on `session_secret` was missing, and PyJWT found it.**
  `-W error` turned its `InsecureKeyLengthWarning` into a failure: a 21-byte key
  is below RFC 7518's floor for HS256. The setting now requires 32 bytes. This is
  the clearest return yet on making warnings fail.
- **A `production()` helper in `conftest`.** Production has guards of its own, so
  flipping only `ENVIRONMENT` built a settings object that failed for a reason
  the test did not intend — the CORS wildcard test in particular would have
  passed on the wrong error.
- **SHA-256 for the refresh token, Argon2 for passwords.** Different inputs:
  256 bits of randomness has no dictionary to slow down.
- **httpx deprecated per-request cookies**; the replay test sets the jar directly.

### Known limitations
- Nothing yet *reads* the access token — the dependency that turns a cookie into
  a current user arrives with protected routes (3.10).
- No device or IP recorded on a session, so "sign out my other devices" (3.6)
  cannot show the user what they are ending.
- Expired sessions are never deleted; a sweep belongs with background jobs (5.7).
- Rotation makes concurrent refreshes race: two tabs refreshing at once can look
  like a replay and sign both out. A grace window is the usual fix; noted for 3.6.

## Follow-up — CI red on collection (2026-09-13)

Adding `session_secret` broke CI in a way that local runs could not show: there
is no `.env` there, only the job's env block, and the secret was not in it.

The missing variable was the trigger; the design flaw was `app = create_app()` at
module scope. That made *importing* the module read and validate the entire
environment, so all twelve test modules failed at **collection** — including
tests that inject their own settings and never touch the real ones.

| Fix | Why |
| --- | --- |
| `SESSION_SECRET` added to the CI job | needed by Alembic and anything reading real settings |
| module-level `app` removed; uvicorn uses `--factory` | importing the module no longer requires a complete environment |

Verified by running the unit suite with `.env` moved away and every managed
variable unset — the state CI is in before its env block applies. It passes.
