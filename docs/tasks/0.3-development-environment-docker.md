# Task 0.3 — Development environment and Docker

## Objective

Make the full local topology runnable with one command: PostgreSQL with pgvector,
Redis, and an S3-compatible object store, alongside the web and API apps.

## Context

Task 0.2 produced two installable apps with no backing services. The API has
dependencies but no application (task 2.1), so compose must bring up
infrastructure that is useful before the API can serve traffic.

`infra/` is reserved for this task in `docs/ARCHITECTURE.md`.

## Prerequisites

- Task 0.2 complete.
- Docker with Compose v2 available locally.

## Implementation steps

1. Create `infra/docker-compose.yml` with:
   - `postgres` — a Postgres image that includes pgvector, named volume,
     healthcheck, non-default credentials read from the environment.
   - `redis` — with a healthcheck and a named volume.
   - `minio` — S3-compatible object storage, console exposed, named volume.
2. Add a development Dockerfile for the API (`infra/api.Dockerfile`) using uv, and
   decide whether the web app runs in a container or on the host for development.
   Record the decision if it is not obvious.
3. Wire compose service ports and a shared network; avoid clashing with common
   local defaults where practical.
4. Add `scripts/dev-up.sh` / `scripts/dev-down.sh` wrapping compose.
5. Document required tooling and the startup sequence for a new contributor.
6. Verify pgvector is actually available (`CREATE EXTENSION vector`).

## Acceptance criteria

- `docker compose -f infra/docker-compose.yml up -d` brings all services healthy.
- `CREATE EXTENSION IF NOT EXISTS vector;` succeeds in the Postgres container.
- Redis responds to `PING`.
- MinIO console reachable and a bucket can be created.
- Data survives a container restart (named volumes).
- No credentials are hard-coded in committed files; compose reads them from the
  environment with development-only defaults clearly marked as such.
- `docker compose down` leaves no orphaned containers.

### Environment findings that shaped the design

1. **Ports 5432 and 6379 were already occupied** by Homebrew `postgresql@16` and
   `redis` launch agents. Publishing on the defaults would have failed to bind, or
   silently connected the app to the wrong database. → ADR-008, non-default ports.
2. **`minio/minio` on Docker Hub returns 401 for anonymous pulls.** Verified
   against the registry API. → ADR-009, pull from quay.io.
3. **PostgreSQL 18 moved its cluster** to `/var/lib/postgresql/18/docker` with the
   image volume at `/var/lib/postgresql`. Read from the image config blob before
   writing the compose file, so the volume mount is correct rather than silently
   non-persistent.

- `CREATE EXTENSION IF NOT EXISTS vector` succeeds — yes; also exercised the type.
- Redis responds to `PING` — yes.
- MinIO console reachable and a bucket can be created — yes, both.

### Deviations from the plan, and why
1. **`docker compose up --wait` needed splitting.** `--wait` treats the one-shot
   `minio-init` container exiting — even with status 0 — as a failure, which under
   `set -e` killed the script before it printed its summary. `dev-up.sh` now waits
   on the three long-running services, then runs the initializer and checks its
   exit code explicitly. Found by running the script, not by reading it.
2. **The API service is behind an `api` profile** rather than started by default.
   It cannot serve anything until task 2.1 creates the ASGI app, so starting it by
   default would mean a permanently failing container. Recorded in ADR-007.
3. **`dev-up.sh` reads the effective ports back from `docker compose port`** rather
   than echoing the defaults, so the summary stays true when `.env` overrides them.

### Known limitations
- The container's interpreter is Python 3.13.15 while the host has 3.13.14 — the
  base image ships a newer patch. `uv.lock` pins the dependencies, so this affects
  the interpreter patch only. If it ever matters, pin the base image by digest.
- `infra/postgres/init/` runs only on first initialization of an empty volume. A
  contributor with an existing volume will not pick up a new init script; task 2.5
  must handle the `vector` extension in a migration for environments not built from
  this compose file.
- `.env` is currently read only by compose. Typed, validated application
  configuration is task 0.5.
- No CI runs any of this yet — task 0.6.
- The MinIO image is pinned to a September 2025 release; see ADR-009.
