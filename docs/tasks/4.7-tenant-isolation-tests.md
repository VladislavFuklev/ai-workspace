# Task 4.7 — Tenant isolation tests

## Objective

One place that tries to cross the tenant boundary, systematically, and fails if
a route is added without an answer to that attempt.

## Context

Phase 4 has isolation assertions in four files, each written next to the feature
it belongs to. That is the right place for them, and it is not enough: they
cover the routes that existed when they were written. The failure this task
guards against is the one nobody notices — a route added in phase 5 or 7 that
takes an id and never asks whose it is.

The test has to be *generated from the application*, not from a list someone
maintains. A hand-written list of routes is a list that goes stale silently,
which is the same failure one level up.

## Implementation steps

1. Enumerate the app's routes from `app.routes`, keeping those whose path
   contains `{organization_slug}`.
2. For each, as a non-member: 404, and a body naming nothing about the tenant.
3. For each, as a signed-out caller: 401.
4. A guard test: every route under `/organizations/{organization_slug}` resolves
   `get_tenant_scope`, so a new one cannot skip the dependency by accident.
5. Repository-level: a `TenantScope` for organisation A cannot read or write
   rows belonging to B.
6. A test asserting the enumeration is not empty and matches the routes that
   exist, so a broken enumeration fails loudly rather than passing vacuously.

**Excluded:** documents and conversations (phases 5 and 7) — this must keep
working when they arrive, which is the point of generating the list.

## Acceptance criteria

- Adding a tenant route with no scope dependency fails the suite.
- Every enumerated route answers 404 to a non-member and 401 to a stranger.
- No refusal body contains the other tenant's name, slug or id.
- The enumeration is asserted non-empty and complete.
- `scripts/check.sh` passes.

### Deviations
- **Routes are discovered from the route *modules*, not from `app.routes`.**
  FastAPI 0.141 mounts included routers lazily, so the application exposes them
  only after a request has matched — an enumeration read from it comes back
  empty and every sweep passes vacuously. That failure mode is exactly what this
  task exists to prevent, so the discovered set is compared with the OpenAPI
  document, which is what the app actually serves.
- **One test per property, looping over the routes, rather than parametrised
  per route.** Discovery needs the app fixture, which is not available at
  collection time. The loop collects every offending route before asserting, so
  a failure names all of them rather than the first.
- **Both halves are kept.** The structural check (the dependency is resolved)
  and the behavioural one (the answer is 404 and says nothing) fail
  independently: a route could resolve the scope and still leak a name in an
  error, and a route could answer correctly today by accident.

### Known limitations
- Only routes whose *path* names the organisation are swept. A future endpoint
  that takes a tenant id in the body or a query parameter would not be found —
  when one is added, that convention needs its own check.
- Documents and conversations do not exist yet. The value of this file is that
  it is already there when they do.
- The repository-level tests name the repositories explicitly; a new
  tenant-scoped repository is not swept automatically.
