# Task 1.2 — Responsive application layout

## Objective

The frame every authenticated screen renders inside: a persistent sidebar on
desktop that becomes a dismissible drawer on small screens, a header, and a
content column — correct at 375px, 768px and desktop.

## Context

Task 1.1 left `(app)/layout.tsx` as a header strip and `<main>`. This gives it a
real structure. Navigation *content* and active states are task 1.4; this task
builds the region they live in and the behaviour around it.

## Implementation steps

1. Client shell component under `src/components/layout/` holding the drawer state;
   `(app)/layout.tsx` stays a Server Component that composes it.
2. Desktop (`lg` and up): sidebar always visible beside the content.
3. Below `lg`: sidebar becomes a modal drawer opened from a header button. Use the
   native `<dialog>` element so focus trapping, `Escape` and inert background come
   from the browser rather than hand-written key handling.
4. Content column with a max width and consistent gutters at every breakpoint.
5. Preserve the 1.1 accessibility contract: skip link first, one `<main>`, focus
   returns to the toggle when the drawer closes.
6. Placeholder nav region — a labelled `<nav>` with nothing in it yet (task 1.4).

**Excluded:** navigation items and active states (1.4), theme switcher (1.5),
reusable state components (1.6).

## Acceptance criteria

- No horizontal overflow at 375px, 768px or 1280px.
- Below `lg` the sidebar is not rendered inline; at `lg` and up the drawer button
  is not rendered.
- The drawer closes on `Escape` and on backdrop click, and focus returns to the
  toggle.
- The toggle has an accessible name and reflects state (`aria-expanded`).
- Long content and long labels do not break the frame.
- `scripts/check.sh` passes.

## Tests

No component tests yet (12.2). Verification is the served markup at each
breakpoint plus the `<dialog>` semantics in the built output.

### Deviations
- **The drawer is a native `<dialog>`.** Focus trapping, `Escape` and an inert
  background come from the browser; a hand-written trap gets those subtly wrong.
  Only opening, closing and returning focus to the toggle are ours, all funnelled
  through the dialog's own `close` event so `Escape` and backdrop behave alike.
- **`Sidebar` takes an `id` prop.** It renders twice — inline and in the drawer —
  and both are in the DOM simultaneously, so a hard-coded `id` produced a
  duplicate that also broke `aria-controls`. Only the drawer instance carries it.

### Known limitations
- Two `<nav aria-label="Main">` landmarks exist, one per breakpoint; only one is
  ever displayed. Standard for a responsive nav, but worth revisiting at 1.4.
- Drawer behaviour (Escape, backdrop, focus return) is reasoned from the `<dialog>`
  contract, not observed — no browser automation until 12.8.
