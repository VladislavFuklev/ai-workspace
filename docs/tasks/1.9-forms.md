# Task 1.9 — Forms and validation

## Objective

Form primitives that carry the accessibility wiring, and one schema that validates
in the browser and describes what the API is sent.

## Context

1.7 gave `ApiError` a structured `detail`; this is what turns a 422 back into
field-level errors instead of a banner the user has to decode.

## Implementation steps

1. `Field` — label bound to the control, description and error both referenced by
   `aria-describedby`, `aria-invalid`, `aria-required`. A render prop, so selects
   and textareas get the same treatment without a component each.
2. `Input` / `Textarea` — styling only.
3. `SubmitButton` — disabled while pending, with the reason announced.
4. `FormError` — form-level failures, with a reference id.
5. `applyServerErrors` — maps the API's field errors onto their fields.
6. A working demo at `(dev)/forms` exercising client validation, a server-side
   field error and a form-level failure.

## Acceptance criteria

- Every control has a bound label; every description and error is referenced.
- Errors are announced (`role="alert"`), not conveyed by colour alone.
- Submit is disabled while pending with a visible pending state.
- A 422 naming a field puts the message on that field.
- `scripts/check.sh` passes.

### Deviations
- **Fixed a bug in 1.7's `ApiError` while writing this.** `errorFromResponse`
  parsed the server's `detail` and then discarded it, so `applyServerErrors` had
  nothing to map. `detail` is now kept on the error.
- **`Field` takes a render prop** rather than wrapping `<input>`. One component
  then covers inputs, textareas, selects and anything later, and the wiring cannot
  be half-applied.
- **The demo lives at `(dev)/forms`.** 1.10 turns `(dev)` into a proper gallery
  around it.

### Known limitations
- The demo submits to a local stub; the real endpoint arrives with phase 3/4.
- Keyboard and screen-reader behaviour is reasoned from the markup, not observed.
