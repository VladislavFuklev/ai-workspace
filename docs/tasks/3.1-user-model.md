# Task 3.1 — User model

## Objective

The first domain table: who a person is, how they are identified, and whether
they may sign in — with a migration that proves the 2.4 base and the 2.5
autogenerate path work on something real.

## Context

`Base`, `UUIDPrimaryKey` and `Timestamps` (2.4) have only ever been exercised by a
throwaway table. Alembic's drift check (2.5) is close to vacuous with no models.
This is the first table, so it is also the first honest test of both.

## Implementation steps

1. `models/user.py` — email, optional password hash, display name, active and
   verified flags.
2. Email is the identity: unique, normalised to lowercase at the boundary so
   `A@b.com` and `a@b.com` cannot both exist.
3. `password_hash` is nullable. A user created through OAuth (3.8) has no
   password, and a nullable column is how that is expressed rather than a
   sentinel.
4. A repository for the queries authentication will need.
5. Migration by autogenerate, reviewed by hand.
6. Tests: constraints, normalisation, the repository, and a drift check that is
   no longer vacuous.

**Excluded:** hashing (3.4), any endpoint (3.2, 3.3), sessions (3.5),
organisation membership (4.2).

## Acceptance criteria

- A second user with the same email in different case is rejected by the database.
- `password_hash` accepts NULL.
- Every constraint follows the 2.4 naming convention.
- The migration applies to an empty database and reverses.
- After `upgrade head`, autogenerate finds no drift — now meaningfully.
- `scripts/check.sh` passes.

## Tests

Unit for normalisation and column configuration; integration for constraints,
the repository and the migration.

### Deviations
- **A functional unique index on `lower(email)`, not a plain unique column.** The
  application normalises, but "we always remember to normalise" is not a
  guarantee, and two accounts differing only by case is account takeover rather
  than untidiness. The database refuses it whatever the code does.
- **The first attempt at that index was silently wrong.** `func.lower("email")`
  compiles to `lower('email')` — an index on a string constant, which protects
  nothing and raises no error. Caught by compiling the DDL and reading it;
  `text("lower(email)")` is correct. Worth remembering: an index that exists is
  not an index that does anything.
- **Defaults are asserted against the database, not the model.** Reading
  `server_default.arg` fails type checking, and the behaviour of a real insert is
  the thing worth asserting anyway.
- **`is_active` and `is_verified` are separate flags.** They answer different
  questions: whether an administrator disabled the account, and whether the
  address was proven. Collapsing them means unverifying someone locks them out.

### Known limitations
- No `last_login_at` or failed-attempt counter; those belong with 3.3 and rate
  limiting (10.5).
- No soft delete. Deleting a user with documents is a phase 5 question.
- Email format is not validated at the column; that is the schema's job (3.2).
