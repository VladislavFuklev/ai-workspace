# Task 4.6 — Resource authorization

## Objective

Give the permissions that currently only exist as names their endpoints: manage
members, change roles, remove people, rename and delete an organisation — each
acting through a `TenantScope`.

## Context

4.3 wrote the rules (`change_role`, `remove_member`, the last-owner guard) and
4.4 wired one dependency, but nothing over HTTP can reach them. Until it can,
the rules are tested in isolation and unused in practice.

This is also where the scope stops being only a permission check and starts
being the thing that scopes a query: every write here names a member *of this
organisation*, and a member of another one must be indistinguishable from one
that does not exist.

## Implementation steps

1. `PATCH /organizations/{slug}` — rename (`organization:update`).
2. `DELETE /organizations/{slug}` — owner only (`organization:delete`).
3. `PATCH /organizations/{slug}/members/{user_id}` — change role.
4. `DELETE /organizations/{slug}/members/{user_id}` — remove, including leaving.
5. Error mapping: the service's refusals must reach HTTP as 403 or 404, never
   500, and never a message naming someone in another organisation.
6. Frontend: the members list on the settings page, with the actions the
   caller's own role allows and nothing it does not.

**Excluded:** invitations and joining (phase 10), the isolation sweep (4.7).

## Acceptance criteria

- Each endpoint refuses a signed-out caller, a non-member, and a member without
  the permission, with the status the surrounding rules already establish.
- Acting on a member of another organisation is a 404.
- The last owner can be neither demoted nor removed, over HTTP as in the service.
- Deleting an organisation removes its memberships.
- The UI offers no action the API would refuse.
- `scripts/check.sh` passes.

## Tests

Integration, through HTTP, one refusal per rule.

## Outcome — completed 2026-09-13

Four endpoints and one settings page. Every action is authorised by the scope,
and the page offers only what the API says the caller may do.

```
PATCH  /organizations/{slug}                    organization:update — the slug never changes
DELETE /organizations/{slug}                    organization:delete — memberships cascade
PATCH  /organizations/{slug}/members/{user_id}  member:role_change
DELETE /organizations/{slug}/members/me         leaving: no permission, last owner refused
DELETE /organizations/{slug}/members/{user_id}  member:remove — never yourself
```

| Check | Result |
| --- | --- |
| signed out, all five | 401 |
| **a non-member, all five** | 404, the same message as a missing organisation |
| a member renaming | 403 naming `organization:update` |
| an admin deleting the organisation | 403; the owner's succeeds, 204 |
| memberships after a delete | gone (`ON DELETE CASCADE`), organisation row gone |
| renaming | name changes, slug does not, old address still resolves |
| an admin promoting to owner | 403 |
| changing your own role | 403 |
| **someone from another organisation** | 404, and the response names neither them nor their tenant |
| an unknown role | 422, before any rule runs |
| an admin removing an owner | 403; removing a member, 204 |
| removing yourself | 403, pointing at leaving |
| a viewer leaving | 204, then 404 for that organisation |
| the last owner leaving | 409 |
| **settings page as owner vs viewer** | rename, one role select (not for self), one remove, delete, leave · vs leave only |
| gate | ruff, mypy, eslint, tsc, contrast, messages, reserved, 181 unit / 128 integration |

### Deviations
- **The API sends the caller's permissions with each organisation.** The page had
  to decide what to render, and the alternative was a copy of the permission
  table in TypeScript — a copy that drifts, where every drift is a button that
  fails when pressed. `OrganizationSummary.permissions` is that answer computed
  once, server-side. It decides what is *offered*; the API still checks.
- **Renaming never changes the slug.** A slug that followed the name would break
  every shared link, bookmark and remembered organisation at once, and the old
  address would silently belong to nobody.
- **Leaving is its own method, not `remove_member(self)`.** It needs no
  permission — a viewer may leave — but keeps the last-owner guard. Removing
  yourself is refused with a message naming the alternative.
- **A 4.3 test changed.** `test_the_last_owner_cannot_be_removed` removed the
  owner *by themselves*, which the new rule refuses earlier. It now asserts both:
  the refusal, and that `leave` is where the last-owner conflict surfaces.
- **Over HTTP the last-owner guard is only reachable by leaving.** Only an owner
  may act on an owner, and nobody may change their own role, so a sole owner has
  nobody able to demote or remove them. The guard stays as defence in the
  service; the tests say which path actually reaches it.

### Known limitations
- No way to add a member yet: memberships come from creating an organisation, so
  the multi-member cases were set up in tests and, for the live check, with SQL.
  Invitations are phase 10.
- No audit trail. Role changes, removals and deletions are logged, but a log is
  not something the organisation's owner can read (10.1).
- Deleting is confirmed by typing the name, which is a client-side gate only.
- The members table's interactions are verified by reading the rendered HTML per
  role, not by driving a browser (12.8).
