# Task 2.6 — Health endpoints

## Objective

Liveness and readiness as separate endpoints, because an orchestrator acts on them
differently and conflating them turns a dependency outage into a restart loop.

## Context

2.1 deliberately left `/` as an identity route rather than a health check. 2.3 and
2.5 supply the dependencies worth checking.

## Implementation steps

1. `/health/live` — checks nothing external. A failure means restart the process.
2. `/health/ready` — checks Postgres and Redis concurrently, with a timeout, and
   returns 503 when any is down. A failure means take it out of the load balancer
   and leave it running.
3. Report the failure type, not the message: the endpoint is often unauthenticated.
4. Mount off the versioned prefix — a probe URL should not change with the API
   version.

## Acceptance criteria

- Liveness answers 200 with an unreachable database.
- Readiness answers 503 when the database is unreachable, and names which check
  failed.
- Readiness answers 503 when only Redis is down, with the database still `ok`.
- Readiness answers 200 when both are reachable.
- The response body carries no host, credential or driver message.
- `scripts/check.sh` passes.

## Tests

Unit for liveness and the failure paths; integration for the healthy path and the
Redis-only failure.

### Deviations
- **`httpx.ASGITransport` does not run the lifespan.** A comment in 2.1's tests
  claimed it did; it dispatches requests only, so the session factory the lifespan
  installs was missing and readiness failed with a `KeyError`. Tests now use a
  `running_app` helper that enters the lifespan, and 2.1's test was corrected to
  assert the real behaviour.
- **Enabled Ruff's `BLE` rule** rather than deleting the `noqa` it reported as
  unused. Catching bare `Exception` is right at a health-check boundary and wrong
  almost everywhere else, so the rule now guards the rest and the two intentional
  cases are marked.
- **A test for an exception escaping a dependency was removed**, not weakened: it
  asserts behaviour task 2.8 has not built yet. Readiness already handles failures
  from the query itself, which is the case that matters here.

### Known limitations
- No storage (MinIO) check. It is not on the request path until phase 5; adding it
  now would fail readiness for a dependency nothing uses.
- The 2 s per-check timeout is a guess until there is production latency data.
